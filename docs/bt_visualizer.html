2行为树的三条基本规则

规则一：每个节点被 tick 时返回三态之一

返回值含义
SUCCESS做完了，成功
FAILURE做不了 / 失败了
RUNNING还没做完，下个 tick 接着做

条件节点只能返回前两个；动作节点三个都可以。

规则二：tick 从根往下传播

主循环每 50 ms 调一次 tree.tickRoot()，根节点把 tick 传给它选中的孩子， 返回值逐层汇总。整棵树的值 = 根节点的返回值。

注意：一帧只走一条路径，不是所有节点都跑一遍。这一点上行为树和 switch 是一样的 —— 区别在"下一帧走哪条"由谁决定。

规则三：节点分三类

类别职责本项目里的例子
控制节点决定孩子的执行顺序，自己不干活 Sequence Fallback ReactiveSequence ReactiveFallback
装饰器修饰一个孩子 RetryUntilSuccessful Timeout ForceSuccess（框架自带）
叶子·条件只读判断，必须瞬时返回，不能阻塞 IsArmed IsOffboard IsAtSetpoint IsTargetVisible
叶子·动作真正干活，可以跨多个 tick Takeoff Hover GotoRelative Orbit Land

两种控制节点的语义（关键）

Sequence（顺序，有记忆）

从左到右 tick 孩子：
  孩子 FAILURE → 整个 FAILURE（进度清零）
  孩子 RUNNING → 整个 RUNNING
                 并记住"我走到第几个孩子"
  孩子 SUCCESS → 下个 tick 去 tick 下一个孩子
  全部 SUCCESS → SUCCESS

这个"记住位置"就是你不用手写 wp_index_ 这类变量的原因。

Sequence vs ReactiveSequence

Sequence          第 2 个孩子 RUNNING 后，
                 第 1 个孩子再也不会被 tick
ReactiveSequence 每帧都从第 1 个孩子重新评估

口诀：要持续监控的条件 → Reactive*；一步一步做完的流程 → 普通版。 这是本项目最容易踩的坑，第 4 节有实测数据。

3状态机 vs 行为树：到底「谁和谁」耦合了

先把一个常见误解纠正掉：状态机并不是"每个任务都判断一下要不要进入对应分支"。 switch 是按 current_state 精确匹配，一轮循环只执行一个 case； 真正的"判断"发生在 case 的末尾给 flight_state_ 赋新值的时候。 它也不比行为树"更扫描"——两者都是每帧只走一条路径。

所以真正的区别是："下一帧走哪条路径"由谁决定，以及"现在做到第几步"存在哪里。

3.1 你原来的 offboard_orbit.cpp：一个变量扛了四件事

enum FlightState { WAIT_FCU, ARM_OFFBOARD, TAKEOFF, HOVER, MOVE, ORBIT, LAND, DONE };
FlightState flight_state_;   // ← 这一个变量同时表示：进度 + 行为 + 转移 + 异常

switch (flight_state_) {
  case TAKEOFF: takeoff(); break;
  case HOVER:   hover();   break;
  ...
}
// 每个 step 函数的末尾，手写"下一步是谁"：
void hover() {
  publishSetpoint(...);
  if (过了 hover_time_) {
      if (!waypoints_.empty()) { flight_state_ = MOVE; }   // ← 转移写在行为里
      else                     { enterOrbitOrLand(); }
  }
}

3.2 拆开看：四件事其实属于四个地方

职责状态机写在哪行为树写在哪
现在做到第几步
（进度）		 flight_state_ 枚举 + 手写跳转 Sequence 的 current_child_idx_（框架持有）
这一步怎么做
（行为）		 case 里调的 takeoff()/hover()/move()，都写在同一个类里 叶子节点类：Takeoff 只管起飞，Orbit 只管绕圈
什么时候进下一步
（顺序）		 散落在每个 case 末尾的 flight_state_ = XXX XML 里孩子的先后顺序，一眼看完
出异常怎么办
（安全）		 主循环里的 if (flying() && mode != "OFFBOARD")，还要维护 flying() 另写一棵子树（ReactiveFallback）或放在树外的看门狗里
进度数据 成员变量 wp_index_ phase_start_ orbit_start_ land_requested_ 框架持有：节点的 IDLE/RUNNING 状态 + 顺序节点的索引
「解耦」就是这个意思：上面这张表的每一行，从同一个 switch 里被搬到了不同的地方。 改"顺序"不用碰"行为"，加"异常"不用碰"任务"，写"行为"的人不用知道整个流程长什么样。
判断标准非常朴素：加一个新需求，你要改几处代码？

3.3 量化对比：加一个「电量低于 20% 立刻返航」

状态机：改 C++、重新编译，4 个函数都要动

- enum FlightState { ..., RTL };
- bool flying() { ... || flight_state_ == RTL; }

  void takeoff() {
+   if (batteryLow()) { flight_state_ = RTL; return; }
    ...
  }
  void hover() {
+   if (batteryLow()) { flight_state_ = RTL; return; }
    ...
  }
  void move()  { + 同样一行 ... }
  void orbit() { + 同样一行 ... }

+ case RTL: if (returnHome()) return; break;

而且返航结束后回不到原来的步骤——状态机没有"记住从哪来"的概念， 除非你再加一个 state_before_rtl_ 变量。

行为树：加 3 行 XML，原有节点代码 0 改动

<ReactiveFallback>

  <Sequence>              <!-- 原来那棵树，一个字没动 -->
    <EnsureOffboard/>
    <EnsureArmed/>
    <Takeoff height="2.0"/>
    <Hover duration="3.0"/>
    <Orbit radius="3.0"/>
  </Sequence>

  <Sequence>              <!-- 新增的异常分支 -->
    <BatteryLow/>
    <ReturnHome/>
  </Sequence>

</ReactiveFallback>

外层 ReactiveFallback 每帧先问"电量低不低"，低了就走返航分支， 任务分支被自动挂起（halt）；电量问题是瞬时的还能回去继续做。

3.4 三种耦合的具体表现

  1. 顺序耦合：状态机把"下一步是谁"写在每个 case 的末尾。 想在全球任一位置插一步，得找到所有指向它的边并改掉；行为树里顺序就是 XML 里节点的排列。
  2. 异常耦合：状态机必须把"OFFBOARD 丢了怎么办"塞进任务循环， 还要维护 flying() 这种"哪些状态算飞行中"的知识——安全逻辑被迫了解任务细节。 行为树里异常是并列的一棵子树，任务树完全不知道安全逻辑的存在。
  3. 数据耦合：状态机的"进度"是散落的成员变量（wp_index_ 等）， 每加一步就可能加一个变量、加一处初始化、加一处复位。行为树里进度由框架统一持有。
别忘了真正的"顺序流"长这样：状态机的转移是边（谁指向谁），行为树的顺序是树的形状。 状态数一多，边会变成网状（N 个状态可能有 N² 条边）；树永远是树， 复杂度随"步骤数"线性增长，而不是随"状态组合"爆炸。

4实测：为什么我一开始把 Sequence 放在 ReactiveFallback 里是错的

我最初写的 aruco_search.xml 是这样的（错的）：

<ReactiveFallback>
  <Sequence>                <!-- ← 这里应该是 ReactiveSequence -->
    <IsTargetVisible timeout="0.5"/>
    <Hover duration="5.0"/>
  </Sequence>
  <Sequence name="方形巡逻"> ... </Sequence>
</ReactiveFallback>

症状：目标（ArUco 标记）从视野里消失后，飞机不会立刻回去巡逻， 而是硬把 5 秒悬停做完。看起来"ReactiveFallback 没起作用"。

原因：ReactiveFallback 确实每帧都从它的孩子 0 开始评估， 但孩子 0 是一个 Sequence，而 Sequence 内部有记忆： 它一旦推进到第 2 个孩子（Hover），第 1 个孩子（IsTargetVisible） 就再也不会被 tick。外层再怎么"从头评估"，里层还是从中间接着跑。

一句话记住：Reactive* 的"反应式"不会穿透孩子。 你自己有记忆，就得自己负责每帧重新判断条件。

另外还确认了一个容易搞错的细节：在 ReactiveSequence 里， 返回 RUNNING 的孩子是继续跑而不是每帧重来 —— 实测 Hover duration="5.0" 恰好持续 100 帧 @20Hz＝5.00 秒后才结束。 （但已返回 SUCCESS 的孩子会被重新 tick，所以官方文档明确警告： 不要在 ReactiveSequence 里放有副作用的动作节点。我们树里前几个孩子都是条件节点，安全。）

还有一个必须知道的特性：任务结束后继续 tick ＝ 重跑

Tree::tickRoot() 在根节点返回 SUCCESS/FAILURE 后， 会把根节点状态重置为 IDLE。实测继续调用 tickRoot()：

tick 20: root=SUCCESS  hover=IDLE      <-- 任务完成
tick 21: root=RUNNING  hover=RUNNING   <-- 整棵树从头又跑了一遍！
tick 22: root=RUNNING  hover=RUNNING

所以 offboard_bt.cpp 的主循环一到终态就 return —— 不然飞机落地后会自己再起飞一次。你也可以在本页按「跳到结束」后再按几次「单步 tick」看到这个现象。

5优缺点：什么时候用哪个

状态机（switch-case）行为树（BehaviorTree.CPP）
优点
  • 状态少（<5）时最直观，一眼看懂
  • 零框架依赖，性能开销最小
  • 调试最简单：打一个变量就知道在哪一步
  • 可以在 case 里写阻塞代码，写起来随意
缺点
  • 状态 × 异常 → 跳转边爆炸（N² 级）
  • 改流程＝改代码＝重新编译
  • 流程没法复用，"巡逻"逻辑换个任务要复制一遍
  • 持续监控（随时可能发生的异常）很别扭
  • 流程只存在于代码里，非程序员无法参与
 优点
  • 流程与实现解耦：加步骤改 XML，不重编译
  • 节点可复用、可组合、可嵌套成子树
  • 天生支持反应式监控（Reactive*）与异常分支
  • 进度由框架持有，不用手写一堆状态变量
  • 可视化调试（Groot）/ 运行时热加载 XML
缺点
  • 多一层抽象，初学要理解 tick / 三态 / 记忆
  • 节点必须非阻塞快速返回，写惯 while 的人容易踩坑
  • 每帧从根走一遍，有开销（本项目 20Hz×十几个节点，可忽略）
  • "进度"是隐式的，不看可视化/日志不好排查
  • 控制频率受 tick 频率限制，不适合做连续控制
结论不是"行为树替代状态机"，而是分工：
  • 行为树适合：任务步骤经常变、需要复用、需要随时监控异常 —— 也就是"决策层"。
  • 状态机适合：状态极少且稳定、或者干脆是硬件时序。
  • 连续控制（PID/姿态/位置环）永远归飞控，行为树只负责"飞去哪、什么时候飞"。
你这个项目正好卡在行为树的甜点上：飞行动作就那么几个（起飞/平移/环绕/降落）， 但任务编排会一直变（对着陆点找标记、巡检、返航、多机协同）， 所以"把动作做成节点、把编排交给 XML"收益最大。

6.2 四个常用模式（直接抄）

① 顺序任务（最常用）

<Sequence>
  <Takeoff height="2.0"/>
  <GotoRelative x="5" y="0" z="2"/>
  <Land/>
</Sequence>

② 永久监控 / 异常兜底

<ReactiveFallback>
  <Sequence>  <!-- 正常任务 -->
    ...
  </Sequence>
  <Sequence>  <!-- 异常分支，可多个 -->
    <BatteryLow/>
    <ReturnHome/>
  </Sequence>
</ReactiveFallback>

③ 重试 + 超时

<RetryUntilSuccessful num_attempts="3">
  <Timeout msec="15000">
    <GotoRelative x="5" y="0" z="2"/>
  </Timeout>
</RetryUntilSuccessful>

④ 复用一段子任务

<BehaviorTree ID="TakeoffAndHover">
  <Sequence><Takeoff/><Hover duration="2"/></Sequence>
</BehaviorTree>

6.3 加一个新动作节点（5 步）

  1. 在 src/bt_nodes.cpp 选基类：持续多帧 → BT::StatefulActionNode； 一帧搞定 → BT::SyncActionNode；只读判断 → BT::ConditionNode。
  2. 构造函数里 ctx_(ctxOf(config)) 拿上下文。
  3. 用 static BT::PortsList providedPorts() 声明端口（＝XML 属性）。
  4. 实现 onStart/onRunning/onHalted（或 tick()）。禁止 while/sleep。
  5. 在文件末尾 registerNodes() 里加一行 factory.registerNodeType<你的类>("标签名");， 然后 catkin_make。

节点里能拿到：ctx_->state（飞控状态/位姿/视觉目标）、 ctx_->streamer->set(x,y,z,yaw)（下发指令）、ctx_->origin_x/y/z（起飞点）、 ctx_->requestOffboard()、ctx_->setArmed()。

7五个必须知道的坑

坑后果 / 正确做法
在节点里写 while / sleep / 长阻塞 整个 tick 卡住 → 推流线程虽然还在发，但**任务反应变慢**、超时判断失真。 正确做法：把等待做成"每帧看一眼，没到就返回 RUNNING"。
条件节点返回 RUNNING 条件节点必须瞬时给出结论；SyncActionNode 返回 RUNNING 框架会直接抛异常。
Sequence 放进 ReactiveFallback 就以为"反应式"了 记忆不会穿透孩子，条件再也不会被重新判断（第 4 节实测）。 要用 ReactiveSequence。
任务结束后继续 tickRoot() 根节点被重置为 IDLE，整棵树从头重跑（飞机会再起飞一次）。 主循环必须一到 SUCCESS/FAILURE 就退出。
拿行为树做连续控制 用错层次。位置/姿态/PID 环是飞控的事；行为树只决定"飞去哪、什么时候飞"。 想平滑跟踪轨迹，应该新增一个"轨迹跟踪"节点，而不是提高 tick 频率。
